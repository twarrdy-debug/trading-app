# CLAUDE.md

Web app for day traders: a trading journal, daily instrument analysis, an economic calendar and signals from educators. The web client comes first. A mobile app (Expo/React Native) will later use the same API. The owner communicates in Polish, and all user-facing strings (API error messages, labels) are in Polish.

## Working agreement

- Work in stages and show the result after each one before moving on. Order: 1) data model + API skeleton (done, extended with CFD/futures, spreads and FX), 2) visual direction (done: Chmura), 3) journal + stats UI (done), 4) daily analysis + swing/equal high-low detection from OHLC, 5) economic calendar (done early), news feed (done early), later: accounts, e-mail, push.
- The frontend must look distinctive, not like a generic AI-generated app. Ask the owner before deciding how tiles and buttons look. The chosen style is **Chmura** ("cloud", chosen 2026-09-27 to replace the heavier "A · Awionika" HUD look): white cards with a soft shadow on a cool grey ground (`card` utility), generous radii, sentence-case labels with no letter-spacing, pill toggles and nav, soft-tinted BUY/SELL and long/short badges, Manrope for everything, numbers included (`font-mono` is Manrope with tabular figures, chosen 2026-10-05 from three proposals at https://claude.ai/artifact/ASYWTMBY2x63aZgfanKqaa; it replaced DM Mono, whose missing bold weights made amounts look smeared). The accent is one of two (`ACCENT_COLORS`, picked in the settings): orange #FFB020 (default) or monochrome (stored as #FFFFFF, drawn as black details on the light theme and white on the dark one, `accentForTheme()`). The mockups are at https://claude.ai/artifact/LFP9zYDRzM8Eyin1CP4voN (board 4). On the light theme the accent is darkened into `--accent-ink` wherever it is a line or text. Keep every visual decision in design tokens (CSS variables) and shared components so the look can be swapped later. There are dark and light themes (switched by the sun/moon icon in the header or in the settings) and the two accents above. Buy/long is green and sell/short is red.

## Layout

npm workspaces monorepo:

- `packages/shared`: code shared by the API, web and mobile clients. It holds enums, Zod request schemas (`schemas.ts`), pip/tick/R math (`trade-math.ts`), the signal text parser (`signal-parser.ts`) and date helpers. It is consumed as TypeScript source with no build step.
- `apps/api`: Fastify 5 + `fastify-type-provider-zod` + Drizzle ORM on PostgreSQL.
  - `src/db/schema.ts`: all tables. Migrations are in `apps/api/drizzle/`.
  - `src/routes/*`: HTTP routes. Business logic lives in `src/services/` (the trade logic is in `services/trades.ts`).
  - `src/plugins/current-user.ts`: resolves `req.user`, plus the `requireRole()` helper.
- `apps/api/src/types.ts`: JSON response types for clients (`import type { Trade } from '@trading/api/types'`). They are derived from the service return types, so an API change surfaces as a type error in the web app. The Fastify decorations live in `src/fastify-context.ts` so this import doesn't pull in the whole app.
- `apps/api/src/i18n.ts`: API messages in Polish and English (see Language below).
- `apps/web`: React 19 + Vite + TanStack Query/Router + Tailwind v4.
  - `src/styles.css`: **all design tokens** (colors per theme, fonts, radii, shadows) as CSS variables mapped into Tailwind (`bg-panel`, `text-dim`, `bg-accent`, `text-accent-ink`…). `--accent` and `--on-accent` are set at runtime from the user's settings (`lib/theme.ts`), and `public/theme-init.js` (loaded by index.html, a file because the CSP forbids inline scripts) applies the last used theme before the first paint.
  - `src/components/ui/`: Button, Panel, Field/Input/Textarea/Segmented/`toggleClass`, Select (themed list), Stat/Gauge/Segments. Screens use only these components and tokens, never raw colors, so the look can be swapped in one place.
  - `src/components/charts/`: EquityChart (d3-scale/d3-shape SVG with crosshair tooltip) and BarList (HTML bars that double as the table view).
  - `src/features/*`: the screens (journal, stats, calculator, analysis, calendar, news, settings, account).
  - Settings are a page, `/ustawienia/<section>` (`features/settings/SettingsPage.tsx`): a section menu (profile, appearance and language, currency and time, discipline, trading accounts, favourite instruments, news alerts, invitations for admins) and rows of name + help on the left, control on the right. Every change saves itself (toggles at once, text fields on blur or Enter, only when valid); the password change is the one form with a button. `src/api/hooks.ts` holds all React Query hooks. `src/i18n/` holds the UI strings.
  - In development Vite proxies `/api/*` (prefix stripped) and `/files/*` to the API on port 3001.
- `apps/mobile` comes in a later stage.

## Commands

```sh
npm install
npm run dev            # API (http://127.0.0.1:3001, docs at /docs) + web app (http://localhost:5173)
npm run dev:api        # API only
npm run dev:lan        # same as dev, but the web app is also reachable from other devices on the network (no login yet!)
npm test               # vitest: shared unit tests + API integration tests (in-memory DB)
npm run typecheck
npm run build          # production build of the web app
npm run db:generate    # after editing schema.ts: create a new SQL migration
npm run user:login -- --user <e-mail> [--email <new>] --password '<password>'   # give an existing user a login
```

The server applies migrations and seeds (roles, emotions, instruments, and the first admin from `DEV_USER_EMAIL` while no admin exists) on every startup, production included; both steps are idempotent. `npm run db:migrate` and `npm run db:seed` do the same without starting the server.

## Database

- `DATABASE_URL` set to `postgres://…` uses a real Postgres server through postgres.js. Any other value is a PGlite data directory: embedded Postgres in WASM, with no Docker or install needed. The default is `apps/api/.data/pglite`, and `memory://` is used in tests. Docker is not installed on this machine, so development runs on PGlite.
- Only one process can open a PGlite directory, so stop the dev server before running `db:migrate` or `db:seed`.
- Never edit an applied migration. Change `schema.ts` and run `npm run db:generate`. The running dev server (tsx watch) can apply a freshly generated migration right away, so never plan to edit a generated migration afterwards: when data has to be moved, first add it as its own migration (`npx drizzle-kit generate --custom`) and stop the dev server while generating.
- Numeric columns use `mode: 'number'`, so prices and money come back as JS numbers.

## Domain rules

- **Markets:** the app supports CFD and futures (E-mini and Micro). An instrument has `market` (cfd: sized in lots, futures: in contracts), `measureUnit` (pip for forex and gold, including gold futures GC1/MGC1 whose 0.10 tick is the gold pip, point for CFD indices, tick for the other futures), `unitSize` (the price move of one unit) and `unitValue` (quote-currency value per unit per lot or contract). The defaults are in `src/db/seed-data.ts`, for example XAUUSD pip 0.1 = $10/lot, US100/US30/US500 point = $1/lot (this varies by broker), NQ1 tick 0.25 = $5 and MNQ1 = $0.50, and the forex majors (EURUSD, GBPUSD, USDJPY, USDCHF, AUDUSD, USDCAD, NZDUSD: `assetClass` forex, pip 0.0001 or 0.01 for JPY pairs, 10 units of the quote currency per pip per lot, both currencies in `instrument_currencies`). The calendar shows more than two forex pairs as one "Forex · n" chip. Signal symbols are normalized through aliases (`normalizeSymbol`: NAS100 → US100, NQ1! → NQ1…).
- **Parts of a position** (partial closes, since 2026-10-05): the total size is set on the trade; closed in parts, each part (`trade_exits`, named for history) has its own size, take profit, stop loss (defaults to the previous part's) and result: `tp` (closed at its TP), `sl` (at its SL), `be` (at the entry), `manual` (any price) or `open`. The API takes `parts` (price only for `manual`) or, from older clients and the MT5 import, a single `exitPrice` = one part closing everything. Parts may not exceed the position (`partsTooLarge`). The trade's `stopLoss` is the first part's (the initial risk) and `takeProfits` lists the parts' TPs (`takeProfit` = the first). **Pips add up across the closed parts** (+100 and +200 = +300), money follows each part's size, R is that money against the whole position's risk, and the planned RR is the parts' planned profit against that risk. While a part is open the trade is open with `partial: true` and the realised result; once all are closed `exitPrice` is their size-weighted average and `closedAt` the last close, and only then does it count in stats. A trade in parts is **one trade** everywhere (list, stats, streaks, win rate); the per-part pips appear only in the trade's own summary. Trades saved before parts have no rows: the view shows them as one part. Each trade also has `session` (`tradeSession()` from the opening time: asia, london, overlap, newyork, off), and optionally `strategyId` with `checkedRuleIds` (`ruleCheck` in the view).
- **Trades page** (web `/transakcje`, `features/trades/`): the add form on top (`TradeComposer`): direction, instrument, account, open time with the session shown; the **total size first** (lots, or from the risk as % of the balance or an amount via `sizeForRisk()`) and the entry; then TP, SL and the result for the whole position, or with "close in parts" the same per part (`PartsEditor`; a new part copies the previous stop, a split starts as two halves); a summary of result (per-part pips only here), risk and planned RR; **emotions, notes, screenshots and strategy rules always in view**; signal paste, source, spread and FX rate under "Advanced". It remembers the last account, instrument, size mode and strategy per browser. The list below opens a row's editor in place. The journal (`/dziennik`) is an overview (tiles, equity, accounts, monitor) linking to Trades. Dates and times are picked with the themed `components/ui/DateTimePicker.tsx`, never the browser's own picker.
- **Derived trade columns** (`resultUnits`, `pnlQuote`, `pnlAccount`, `riskUnits`, `rMultiple`, `plannedRR`, `tradeDate`) are always recomputed by `computeTradeMetrics()` on create and update. Never write them directly.
- **Account currency** is set per user. `fxRate` (quote → account) is 1 for the same currency. For EUR/USD/GBP/PLN and the majors' quote currencies JPY/CHF/CAD/AUD/NZD (`AUTO_FX_CURRENCIES`) it is fetched automatically: the ECB rate from the day the trade closed, via Frankfurter (`services/fx.ts`), with past days cached in `fx_rates`. The trade form fetches the same rate (`GET /fx-rate`, `useFxRate`) for its risk and margin preview and shows it as the placeholder of the empty rate field. Other currencies need a manual rate, and until one is entered `pnlAccount` stays null and the API returns a warning. `fxRateSource` is `manual` or `auto`. A manual rate survives edits, and sending `fxRate: null` switches back to automatic. Tests inject a fake `FxProvider` through `buildApp({ fx })`, so they never call the network.
- **Daily spreads (CFD):** `daily_spreads` stores the spread per user × instrument × day. Before the first trade of a day, the client calls `GET /spreads/:instrumentId/:date`. If `askUser` is true, it asks for the spread, pre-filled with `suggestion` (the latest earlier day), and saves it with `PUT`. A trade copies that day's spread into `spreadUnits` and computes `spreadCost`. This is informational only: fill prices already include the spread, so P&L isn't reduced.
- **Daily numbering** ("2/26.09.2025 – SHORT") counts all of the user's trades on that local day in the user's time zone, across instruments, ordered by `openedAt`. It is computed with a window function (`selectNumbered`), never stored, and it doesn't change when the list is filtered. `maxTradesPerDay` flags overtrading (`overDailyLimit`, the "LIMIT" badge), counted per trading account like the trading monitor (`accountDayIndex`; trades without an account are their own group), while the daily number stays shared across accounts.
- **Emotions** are a fixed seeded list (`DEFAULT_EMOTIONS`), and a trade can have several.
- **Signals** have 1..n take-profit levels (TP1, TP2…). Signals with prices on the wrong side are rejected, while trades only get warnings. A trade linked to a signal gets `source = educator` and inherits the signal's educator.
- **Roles:** admin, educator, user, vip. Permissions per role are still to be designed. For now only publishing signals (educator/admin) and managing instruments or educators (admin) are restricted.
- **CFD ↔ futures calculator** (web `/kalkulator`, logic in `packages/shared/src/instruments.ts`): every pair in `CFD_FUTURES_PAIRS` (US100↔NQ1/MNQ1, US500↔ES1/MES1, US30↔YM1/MYM1, XAUUSD↔GC1/MGC1), picked at the top (remembered, basis settings stored per pair), with a single-price converter and IN/SL/TP1/TP2 levels. Mini and micro are **one futures side** ("NQ1 / MNQ1": same price, same tick); the level tiles show the money per contract for both. Distances read in the CFD's unit (pips for gold, points for indices). The difference between the markets comes from server measurements ("Auto"), from two current prices, converted by point difference (`offset`) or price ratio (`ratio`), or from a point offset the user types. Futures prices are rounded to the tick, and risk and reward per contract come from the instruments' `unitSize`/`unitValue`. `services/basis.ts` fetches the reference price (Yahoo ^NDX/^GSPC/^DJI, spot gold from gold-api.com) and the futures (Yahoo NQ=F/ES=F/YM=F/GC=F) every `BASIS_INTERVAL_HOURS` (default 4, 0 = off) and on `POST /basis/refresh`, into `basis_snapshots`. A snapshot is `live` only when both quotes are fresh and within 20 minutes of each other. Alerts compare the last two live snapshots against `alertPoints` per pair (gold 2, US100 10, US500 3, US30 30). These sources are unofficial: fine for personal use, but they must be replaced by a licensed feed before other users rely on them. Tests inject a fake `QuoteProvider` through `buildApp({ quotes })`.
- **Position size:** CFD lots can be fractional (the form offers 0.01 / 0.1 / 0.5 / 1, ×2 and a step button). Futures must be whole contracts, which the API enforces. The journal form has no fees field, but the API still accepts `fees`.
- **Trading monitor** (`GET /trades/monitor`, `tradingMonitor()`): per trading account (`groups`, plus a group for trades without an account when there are some today, or no accounts at all), today's trades against `maxTradesPerDay` and today's losses counted as described under "Losses warning"; the limits from the settings apply to each account separately. One selected account gets the full monitor, "all accounts" a compact row per account. When any group reaches the threshold the web app shows a page-wide banner naming the accounts. Dismissing it is stored per set of `alertKey`s, so the banner returns after the next loss.
- **Economic calendar** (`services/calendar.ts`, web `/kalendarz`): the free Forex Factory feed (`ff_calendar_thisweek.json`) only covers the current week and has no actual values. It is fetched every `CALENDAR_INTERVAL_HOURS` (default 2, 0 = off) and on `POST /calendar/refresh` (at most once every 10 minutes, because FF blocks aggressive polling). Each import replaces that FF week (Sunday to Sunday, New York time) in `economic_events`, so rescheduled events don't duplicate, and older weeks are kept, so history builds up over time. `category` comes from `categorizeEvent(title)` (shared/calendar.ts). Affected instruments come from `instrument_currencies`. Impact flags use FF colors. The views are day, week and month, filtered by currency, impact, category and instrument.
- **News** (`services/news.ts`, `routes/news.ts`, web `/news`, parser in `shared/news.ts`): headlines from FinancialJuice, which has no official API; both sources below are fine for personal use but must be replaced by a licensed feed before other users rely on them. The main source is the site's own undocumented guest API (`live.financialjuice.com/FJService.asmx/Startup`, with the guest token `var info = '…'` scraped from `www.financialjuice.com/home` and cached 6 h): the latest 20 headlines with FJ's tags (`Labels`, currency codes are merged into `currencies`) and the **red marking** (`important`: `Level` contains `active`, or `Breaking`), which the web app paints like FJ (`--breaking` #b80101). Its `DatePublished` has the right UTC time but sometimes a wrong day, so the day is rebuilt (`parseFjApiNews`). After a start it pages back one `GetPreviousNews` page per poll (up to 12 h) so older headlines get their marking; a headline marked red later is pushed to the stream only if under 15 min old. If the site API fails, the RSS (`feed.ashx?xy=rss`: titles only, last 100 ≈ 8 h, no marking) is used instead (`feed.mode = 'rss'`), and the first poll after a start always uses the RSS to fill the gap. Polling runs every `NEWS_INTERVAL_SECONDS` (default 60, 0 = off). `www` answers 429 to roughly the third request within a minute from one IP (every poller on the same public IP counts); `live` tolerated more. After an error the scheduler backs off (doubling, at least Retry-After, at most 10 min). New headlines go into `news_items` (unique per RSS guid, history builds up) with tags from `parseNewsTitle()`: category (`NEWS_CATEGORIES`), currencies, assets (asset classes, for the instrument filter), speaker, outlet, released value (`data`: actual/forecast/previous) and `noise` (FJElite, rate probabilities, correlation/volatility charts; hidden unless `noise=true`). Released values are matched to a calendar event (same currency, scheduled 20 min before to 3 min after, `eventTitleScore()` plus the same forecast) and fill its `actual`, which Forex Factory lacks. `GET /news/stream` is server-sent events (`event: news`, the new headlines as JSON); the web app opens it once in AppShell (`lib/news-live.ts`), so keyword and red-headline alerts (`users.newsKeywords`; sound, notifications and "alert on red" set per browser) work on every screen and the menu shows a dot for unseen matches.
- **Red news during a trade:** each trade in the API has `redNews` (id, title, publishedAt): headlines marked red (`news_items.important`, not noise) published between `openedAt` and `closedAt` that concern the trade's instrument (`newsAffectsInstrument()`, shared/news.ts: one of its calendar currencies, its market via `assets`, or geopolitics for metals; the news `instrumentId` filter uses the same rule); empty for open trades. The journal table shows a white "N" on the FJ red (`bg-breaking`) next to the exit price, with the headlines in its tooltip. Only trades after the news feed started have data.
- **Language:** each user picks `pl` or `en` (`users.language`, settings page). The API translates errors, warnings, emotion labels, stats labels and new checklist items into that language: throw `badRequest('key', params)` with a key from `apps/api/src/i18n.ts`, and custom Zod messages are keys too (`validation.*`). The web client keeps all UI strings in `apps/web/src/i18n/pl.ts` and `en.ts` (same shape, checked by TypeScript) and reads them with `useT()`. Numbers and dates are formatted in the language's locale (`lib/format.ts`). Instrument names are English in every language.
- **MT5 import** (`POST /trades/import/mt5`, `services/mt5-import.ts`, parser in `shared/mt5-report.ts`): reads the MT5 account history report, as HTML (UTF-16) or Open XML (.xlsx). Only the Positions section is used, and rows are recognised by shape, so reports in any terminal language work. Times are platform server time: `broker-ny7` (New York + 7 h, GMT+2/+3, most brokers) or an IANA zone. Broker symbols are matched with `matchBrokerSymbol` (suffixes such as `.cash` or `m`, aliases, futures month codes), and the rest are assigned by the user (`symbolMap`). `commit=false` only previews. Imported trades get `externalId` `mt5:<account>:<position>` (unique per user), so re-importing skips them. Commission and swap become `fees`.
- **Signal direction:** `detectDirection()` (shared/trade-math.ts) reads BUY/SELL from the levels: a stop above the entry is a SELL, below is a BUY, and without a stop TP1 decides. The calculator uses it and shows the converted signal as stat tiles (direction + IN/SL/TP1/TP2).
- **Trading accounts (required for trades since 2026-10-05):** a user can have several accounts (`trading_accounts`, managed on the settings page through `/accounts`): name, `live` or `prop`, size, CFD leverage, and for prop accounts a market (`cfd`/`futures`, required), a maximum drawdown % (required) with a `drawdownType`, and an optional profit target %. A `static` floor is size × (1 − maxDrawdownPct); an `eod` floor trails the highest closing balance of a finished day (days in the user's time zone) minus the limit and stops at the starting size. Every new trade and every MT5 import must name an account (`accountId`, `validation.accountRequired`); saving an edit of an older trade without one is refused (`accountRequired`) until one is chosen. The column stays nullable: trades from before the rule and trades of a deleted account (deleting keeps them) have none and still show under the `none` filter. A prop account only accepts trades from its market. The trade form asks for an account (with a link to the settings when there is none). Balances are the size plus the results of the account's closed trades (`services/accounts.ts`). The journal and stats take an `account` filter (an id, `none`, or omitted for all), chosen with the shared switcher (`lib/account-filter.ts`). Stats return `accounts` (every account's figures), `account` (the selected one) and `summary.returnPct`/`maxDrawdownPct` against it. A daily loss limit and intraday trailing drawdown are not implemented. `summary.maxDrawdown` (money) is always reported.
- **Risk and margin:** each trade in the API has `riskAccount` (stop distance × unit value × size × FX, `riskQuote()`) and `riskPct` (against its account's balance when the trade was opened; null without an account). The journal table shows both (risk % and SL in money). An account's `leverage` (1:10 … 1:1000, optional) makes the trade form show the CFD margin (`marginQuote()` = notional / leverage); futures margins are set by the exchange and are not calculated.
- **Journal tiles:** win rate, average R, result today (stats for the user's local day), result this month and profit factor, all for the account picked in the switcher. Five in a row from 1400 px, in pairs below (arbitrary breakpoints go in rem, since Tailwind sorts px ones before `sm:`).
- **Equity chart against the account:** with one account selected and no instrument filter, stats return `balanceCurve` (that account's balance before the first day and after each day), and the chart plots the balance with reference lines for the start, the prop drawdown floor and the profit target.
- **Losses warning:** the threshold is per user (`users.lossStreakAlert`, 1–20, default 3) and `lossAlertMode` decides what is counted: losses in a row (`streak`, default) or every losing trade of the day (`day`, a checkbox in the settings). The monitor returns `lossMode` and `lossLimit`, and per group `lossCount`, `alert` and `alertKey`.
- **Header clock** (`layout/SessionClock.tsx`, logic in `shared/sessions.ts`): time and date in the user's zone plus a 24-hour strip of the FX sessions (Sydney 07–16, Tokyo 09–18, London 08–17, New York 08–17, each in its own city's time, Monday to Friday); open ones in `--accent-ink`, the tooltip says when each opens or closes. A click opens the "Sessions" panel (modelled on Forex Factory's): hour axis of the user's day, one staggered bar per session labelled with the city's local time, a now line, and the city's bank holiday (calendar events with impact `holiday`, currency AUD/JPY/GBP/USD, `isBankHoliday()` skips daylight saving shifts) drawn instead of the session, which then counts as closed. The theme switch is a single sun/moon icon (showing the theme in use); the settings button is a classic cog with the label "Ustawienia" (the label is hidden between the lg and xl breakpoints, where the menu and clock fill the header).
- **Dashboard** (web `/`, the start page and first in the menu; the journal is at `/dziennik`, `features/dashboard/`, layout modelled on screenshots the owner supplied, drawn with the Chmura tokens): account switcher and a period (all time, this month, 30/90 days, this year; remembered per browser); tiles for net P&L (with sparkline), profit factor (0–3 scale: red < 1, amber to 1.5, greens), win rate (half ring wins/losses) and average win/loss; recent closed trades with TP/SL/BE badges (`exitReason()`, shared/trade-math.ts); a progress heat map of the last 12 weeks by result or discipline with today's checks; the cumulative daily result (`EquityChart polarity`: green above zero, red below); a month calendar with weekly totals (Monday first in Polish, Sunday in English, independent of the period); W/L/BE streaks of the last 30 trades; results by instrument. It reads `GET /trades/stats`, whose `equityCurve` days also carry `trades`, `wins`, `losses` and `discipline` (`DISCIPLINE_CHECKS`: within the trade limit, a stop loss on every trade, emotions on every trade, losses warning not reached; per account like the monitor), plus `summary.breakevens` and `streaks`.
- **Breakeven (BE):** a closed trade within ±`BREAKEVEN_R` (0.1R) of zero, or exactly zero without a stop loss, is neutral (`tradeOutcome()`, shared/trade-math.ts): neither a win nor a loss. Win rate is wins / (wins + losses), the averages of wins and losses leave BE out, and the losses warning, streaks and discipline count only losses. Profit factor still uses all money. Each trade in the API has `outcome` (win/loss/breakeven, null while open) and `pnlPct` (result as % of its account's balance when opened).
- **Journal trade list** (`features/journal/TradeTable.tsx`, modelled on a screenshot from the owner): a table with rows tinted by outcome (green win, red loss, amber BE, accent edge while open): open button, date with daily number, duration and close time, account, instrument badge (`components/ui/InstrumentBadge.tsx`) with entry → exit and the red news mark, direction, result with pips, fees, profit %, risk % with SL money, R with the plan, and a TP/SL/BE (or win/loss/open) badge. The header has the period, a filters toggle, MT5 import, CSV export of the loaded rows and "+ New", which empties and scrolls to the form.
- **First-run introduction** (`features/onboarding/Onboarding.tsx`): `users.onboarded_at` is null after a sign-up (`finishSignUp`) and set by `POST /me/onboarding`; existing users and users created outside sign-up got a date, so they skip it. `/me` returns `onboarded`, and AppShell shows the wizard instead of the app until it is true: account currency and time zone, favourite instruments, a trading account ("Next" needs one, or "later"), a first strategy with its rules, and a summary. Every step saves right away; "Skip" finishes it. `DELETE /me/onboarding` (Settings → Profile, "Run it again") shows it again.
- **Admin panel** (web `/admin/<section>`, `features/admin/`, menu item for the admin role only; API `routes/admin.ts`, `services/admin.ts`, every `/admin/*` route requires admin): **users** (list with role, sign-up date and code, last activity from `auth_sessions`, counts of trades/accounts/strategies, status; change role, block/unblock via `users.disabled_at` (blocked: sign-in refused with `ACCOUNT_DISABLED`, API answers 403 `accountDisabled`, sessions removed), sign out everywhere, e-mail a password reset, delete with all data and screenshot files; never on yourself (`adminSelf`); an educator still linked to signals or others' trades cannot be deleted (`userLinked`)), **statistics** (users, active 7/30 days, trades, accounts and strategies, sign-ups per week, roles, group codes with sign-ups from `users.signup_code`), **system status** (version from `APP_VERSION` or a `VERSION` file at the repository root written on deploy, database, mail, news feed, calendar, CFD/futures measurements, with refresh buttons; refetched every 30 s), **instruments** (all, hidden ones too; edit everything but symbol and market, `PATCH /admin/instruments/:id`; unit changes only affect trades saved afterwards) and **invitations** (moved here from the settings).
- **Public landing page** (`/start`, `features/landing/LandingPage.tsx`, strings in `landing`; slogan chosen by the owner: "Improve your trading to the next level", in Polish "Wznieś swój trading na wyższy poziom"): what the app does, for signed-out visitors; a guest opening `/` is sent there (other paths go to the sign-in page). The preview uses the real dashboard components on invented sample data (never a user's results), and the call to action follows `REGISTRATION` (invite, open, closed). It does not name the unofficial news sources.
- **Favourite instruments** (`favorite_instruments`, `PUT`/`DELETE /instruments/:id/favorite`, settings section "Ulubione instrumenty", grouped Forex / other CFDs / futures): `GET /instruments` marks the user's favourites with `favorite`. Every instrument drop-down builds its options with `instrumentOptions()` (`lib/instruments.ts`), which lists the favourites first under their own heading; use it for any new instrument list.
- **Instrument logos** (`components/ui/InstrumentBadge.tsx`, files in `apps/web/public/logos`, see its README): circular flags from circle-flags (MIT), two overlapping for a currency pair (base, quote), the US flag for US indices and their futures, a gold disc drawn for the app for gold; others get two letters. TradingView's own logo files are not copied (their assets; index logos are trademarks).
- **Metric explanations:** every dashboard tile and panel has a "?" (`components/ui/InfoTip.tsx`) opening a card with what it shows, how it is calculated, how to read the scale and where the data comes from (`dashboard.info` in the i18n files). Keep them in step when a calculation changes.
- **Drop-down lists** use the themed `components/ui/Select.tsx` (select-only combobox), never a native `<select>` or `<datalist>`, whose menus follow the operating system instead of the app theme.
- **Statistics** no longer report a spread cost total (the owner found it unnecessary). Trades still store `spreadUnits`/`spreadCost`.
- **Strategies** (`services/strategies.ts`, `routes/strategies.ts`, web `/analiza` → "Moje strategie", `features/analysis/AnalysisPage.tsx`): a user's strategies (`strategies`: name, optional description) with ordered entry rules (`strategy_rules`, up to `MAX_STRATEGY_RULES`): the conditions the chart must show for an entry to follow the strategy. The user creates a strategy by name, then adds, edits, reorders (dragged by the handle, or ↑/↓ on the focused handle; `PUT /strategies/:id/rules/order` with every rule id) and deletes rules; every rule change returns the whole strategy. Name and description save on blur like the settings page. Each rule has a checkbox for checking an entry before taking it: the panel shows ticked/total and "entry follows the strategy" or how many are missing, with "Clear" for the next setup; the ticks are kept per strategy in the browser (`localStorage`), not on the server. Not linked to trades yet.
- **Checklist:** one per user × instrument × day. It is created on first read with the default items, and the response also includes higher-timeframe levels (H4+) and that day's economic events for the instrument's currencies.

## Accounts and login

- **Better Auth** (`apps/api/src/auth.ts`) handles e-mail + password accounts, cookie sessions (30 days), password reset and rate limits (production). It uses our tables: `users` is the Better Auth user (`name` ↔ `displayName`), plus `auth_sessions`, `auth_accounts` (the password hash sits in `providerId = 'credential'`) and `auth_verifications`. It is mounted at `/auth/*` in the API (`routes/auth.ts`), so the web app calls `/api/auth/*`. `PUBLIC_URL` must be the web app's address, and `AUTH_SECRET` (32+ characters) is required in production.
- **Passwords** follow `passwordProblems()` (`packages/shared/src/password.ts`, since 2026-10-07): at least 10 characters with a lowercase letter, an uppercase letter and a special character (neither letter nor digit). The API enforces it on sign-up, password reset and change (a Better Auth `before` hook, code `PASSWORD_TOO_WEAK`) and in `npm run user:login`; the forms tick the rules live (`components/ui/PasswordRules.tsx`). Passwords set before the rule keep working until changed.
- **Two-step sign-in (2FA, optional per user):** Better Auth's `twoFactor` plugin with authenticator-app codes (TOTP) and 10 backup codes, both stored encrypted with `AUTH_SECRET` (`auth_two_factors`, `users.two_factor_enabled`). Settings → Profile turns it on (password → QR code from `components/ui/QrCode.tsx` (uqr) and the key → first code → backup codes shown once, to copy or download), off, or replaces the backup codes. With it on, `/auth/sign-in/email` answers `twoFactorRedirect` without a session, and the sign-in page asks for the code (or a backup code), optionally trusting the browser for 30 days. Ten wrong codes lock the account for 15 minutes. An admin can turn it off for a user who lost both (`POST /admin/users/:id/two-factor/reset`, ends their sessions).
- **Registration** follows `REGISTRATION`: `invite` (default: sign-up needs a code from `/invites`, created by an admin in the settings; the code sets the new user's role), `open`, or `closed`. An invite can have its own code (4–32 letters, digits, dashes, stored upper-case, unique) and no expiry, and can be a **group code** (`multiUse`): any number of sign-ups, counted in `useCount`, until it expires or is deleted (e.g. `DIXIGROUP26` on production). Single-use invites set `usedBy` instead. Sign-up also stores the browser's language and time zone.
- **Current user** (`plugins/current-user.ts`): from the session cookie; without one the API answers 401 and the web app sends the user to `/logowanie` (and back afterwards). In development `AUTH_DEV_BYPASS=true` (default) keeps the old behaviour: without a session every request acts as `DEV_USER_EMAIL`, and `x-user-id` switches user. The bypass is always off in production, and the API docs (`/docs`) are only served outside production.
- **E-mail** goes through `services/mailer.ts` (`app.mailer`): `SMTP_URL` (any SMTP server as a URL; production uses Resend, `smtps://resend:<key>@smtp.resend.com:465`) from `MAIL_FROM` (test domain: `noreply@twardy.it`). Without `SMTP_URL`, messages (including reset links) are written to the API log. It sends password resets and invitations: an invite created with an address is e-mailed there in the admin's language (`emailed` in the response; the invite stays if sending fails). Tests inject a fake mailer through `buildApp({ mailer })`.
- **Deployment** (`deploy/`, guide in `deploy/README.md`, in Polish): one Debian 12 LXC on Proxmox with PostgreSQL, the API as a systemd service (`npm start` in `apps/api`, `.env` from `deploy/env.production.example`) and Caddy on :8080 doing what the Vite proxy does in development (`/api/*` without the prefix and `/files/*` to the API, the rest from `apps/web/dist`). Cloudflare Tunnel (test domain twardy.it) forwards to Caddy. Better Auth reads the client IP from `CF-Connecting-IP` for its rate limits. Updates: `deploy/update.sh`. **Docker variant (the one in use):** `Dockerfile` (targets `api`: Node running the source with tsx; `web`: Caddy with the built app, `deploy/docker/Caddyfile`) and `docker-compose.yml` (db PostgreSQL 16, api, web on :8080) on a Debian VM, `.env` in the repository root from `deploy/docker/env.example`; guide in `deploy/DOCKER.md`.
- **Existing data:** the seeded admin owns the data created before login existed. Give it a login with `npm run user:login -- --user admin@trading.local --email <your e-mail> --password '<password>'` (stop the dev server first, PGlite allows one process).

## Security

- **Authorization by route, never by the raw URL:** `req.url` is the raw path, and a percent-encoded one ("/%61dmin/users") reaches the same route. The public paths in `plugins/current-user.ts` are matched on `req.routeOptions.url`, and `/admin/*` is checked by a hook that runs for every route of `routes/admin.ts`. A real bypass of this kind existed until 2026-10-07; the admin panel test covers it.
- **Request limits** (`@fastify/rate-limit`, `buildApp({ rateLimits })`, off in tests unless a test turns them on): 300 requests a minute per client IP (`clientIp()`: `CF-Connecting-IP` behind Cloudflare), lower on costly routes through `config.rateLimit` (basis refresh 3, calendar refresh 5, MT5 import 10, screenshot upload 30, admin password reset and news refresh 5, invites 20 a minute). A refusal is 429 `tooManyRequests`. Give any new route that calls outside services, sends e-mail or parses files its own lower limit. Better Auth keeps its own limits on sign-in, sign-up and password reset. The news stream allows `MAX_STREAMS_PER_USER` (8) open connections per user.
- **Uploaded archives:** `xlsxRows()` refuses an .xlsx whose read parts declare more than `MAX_UNPACKED_BYTES` (64 MB) unpacked, so a zip bomb cannot exhaust memory.
- **Outside data:** news links reach the client only as http(s) (`webLink()`).
- **HTTP headers** come from Caddy (`deploy/docker/Caddyfile`, same block in `deploy/Caddyfile`): visitors on plain http (Cloudflare's `Cf-Visitor`) are redirected to https, plus CSP (`script-src 'self'`, no inline scripts; `style-src` allows inline because components set style attributes), HSTS, `X-Frame-Options: DENY`, `nosniff`, Referrer-Policy, Permissions-Policy. A new outside resource (font, script, image host, API) needs the CSP extended or it will be blocked in production while working in development.

## Conventions

- Money in the web app goes through `formatAmount(value, currency)` (`lib/format.ts`): USD amounts are written with `$` ("+$1215,00") and never with the code "USD"; other currencies keep their code after the number. Separate currency captions use `currencyLabel()`, which is empty for USD. Instrument prices stay plain numbers.
- Validate every request with a Zod schema from `@trading/shared` so clients can reuse it.
- Throw `HttpError` / `notFound()` / `badRequest()` from `src/errors.ts`. Validation errors come back as `{ error, issues[] }` with status 400.
- Every query on user data must filter by `req.user.id`.
- Screenshots are saved to `UPLOAD_DIR` and served at `/files/<key>` only to the owner of their trade (404 for anyone else, `Cache-Control: private`). Uploads are recognised by their first bytes (PNG, JPEG, WebP), never by the type the browser declares. They should move to S3/R2 later.

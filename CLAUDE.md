# CLAUDE.md

**AlphaLogFX** (domain alphalogfx.com, name chosen 2026-10-15; `APP_NAME` in `shared/app.ts`): a web app for day traders: a trading journal, daily instrument analysis, an economic calendar and signals from educators. The web client comes first. A mobile app (Expo/React Native) will later use the same API. The owner communicates in Polish, and all user-facing strings (API error messages, labels) are in Polish.

## Working agreement

- Work in stages and show the result after each one before moving on. Order: 1) data model + API skeleton (done, extended with CFD/futures, spreads and FX), 2) visual direction (done: Chmura), 3) journal + stats UI (done), 4) daily analysis + swing/equal high-low detection from OHLC, 5) economic calendar (done early), news feed (done early), later: accounts, e-mail, push.
- The frontend must look distinctive, not like a generic AI-generated app. Ask the owner before deciding how tiles and buttons look. The chosen style is **Chmura** ("cloud", chosen 2026-09-27 to replace the heavier "A · Awionika" HUD look): white cards with a soft shadow on a cool grey ground (`card` utility), generous radii, sentence-case labels with no letter-spacing, pill toggles and nav, soft-tinted BUY/SELL and long/short badges, Manrope for everything, numbers included (`font-mono` is Manrope with tabular figures, chosen 2026-10-05 from three proposals at https://claude.ai/artifact/ASYWTMBY2x63aZgfanKqaa; it replaced DM Mono, whose missing bold weights made amounts look smeared). The accent is one of two (`ACCENT_COLORS`, picked in the settings): orange #FFB020 (default) or monochrome (stored as #FFFFFF, drawn as black details on the light theme and white on the dark one, `accentForTheme()`). The mockups are at https://claude.ai/artifact/LFP9zYDRzM8Eyin1CP4voN (board 4). On the light theme the accent is darkened into `--accent-ink` wherever it is a line or text. Keep every visual decision in design tokens (CSS variables) and shared components so the look can be swapped later. There are dark and light themes (switched by the sun/moon icon in the header or in the settings) and the two accents above. Buy/long is green and sell/short is red.

## Layout

npm workspaces monorepo:

- `packages/shared`: code shared by the API, web and mobile clients. It holds enums, Zod request schemas (`schemas.ts`), pip/tick/R math (`trade-math.ts`), the signal text parser (`signal-parser.ts`) and date helpers. It is consumed as TypeScript source with no build step.
- `apps/api`: Fastify 5 + `fastify-type-provider-zod` + Drizzle ORM on PostgreSQL.
  - `src/db/schema.ts`: all tables. Migrations are in `apps/api/drizzle/`.
  - `src/routes/*`: HTTP routes. Business logic lives in `src/services/` (the trade logic is in `services/trades.ts`).
  - `src/plugins/current-user.ts`: resolves `req.user`, plus the `requireRole()` helper.
- `apps/api/src/types.ts`: JSON response types for clients (`import type { Trade } from '@trading/api/types'`). They are derived from the service return types, so an API change surfaces as a type error in the web app. The Fastify decorations live in `src/fastify-context.ts` so this import doesn't pull in the whole app.
- `apps/api/src/i18n.ts`: API messages in Polish and English (see Language below).
- `apps/web`: React 19 + Vite + TanStack Query/Router + Tailwind v4.
  - `src/styles.css`: **all design tokens** (colors per theme, fonts, radii, shadows) as CSS variables mapped into Tailwind (`bg-panel`, `text-dim`, `bg-accent`, `text-accent-ink`…). `--accent` and `--on-accent` are set at runtime from the user's settings (`lib/theme.ts`), and `public/theme-init.js` (loaded by index.html, a file because the CSP forbids inline scripts) applies the last used theme before the first paint.
  - `src/components/ui/`: Button, Panel, Field/Input/Textarea/Segmented/`toggleClass`, Select (themed list), Stat/Gauge/Segments. Screens use only these components and tokens, never raw colors, so the look can be swapped in one place.
  - `src/components/charts/`: EquityChart (d3-scale/d3-shape SVG with crosshair tooltip) and BarList (HTML bars that double as the table view).
  - `src/features/*`: the screens (journal, stats, calculator, analysis, calendar, news, settings, account).
  - Settings are a page, `/ustawienia/<section>` (`features/settings/SettingsPage.tsx`): a section menu (profile, appearance and language, currency and time, discipline, trading accounts, favourite instruments, news alerts, invitations for admins) and rows of name + help on the left, control on the right. Every change saves itself (toggles at once, text fields on blur or Enter, only when valid); the password change is the one form with a button. `src/api/hooks.ts` holds all React Query hooks. `src/i18n/` holds the UI strings.
  - In development Vite proxies `/api/*` (prefix stripped) and `/files/*` to the API on port 3001.
- `apps/mobile` comes in a later stage.

## Commands

```sh
npm install
npm run dev            # API (http://127.0.0.1:3001, docs at /docs) + web app (http://localhost:5173)
npm run dev:api        # API only
npm run dev:lan        # same as dev, but the web app is also reachable from other devices on the network (no login yet!)
npm test               # vitest: shared unit tests + API integration tests (in-memory DB)
npm run typecheck
npm run build          # production build of the web app
npm run db:generate    # after editing schema.ts: create a new SQL migration
npm run user:login -- --user <e-mail> [--email <new>] --password '<password>'   # give an existing user a login
```

The server applies migrations and seeds (roles, emotions, instruments, and the first admin from `DEV_USER_EMAIL` while no admin exists) on every startup, production included; both steps are idempotent. `npm run db:migrate` and `npm run db:seed` do the same without starting the server.

## Database

- `DATABASE_URL` set to `postgres://…` uses a real Postgres server through postgres.js. Any other value is a PGlite data directory: embedded Postgres in WASM, with no Docker or install needed. The default is `apps/api/.data/pglite`, and `memory://` is used in tests. Docker is not installed on this machine, so development runs on PGlite.
- Only one process can open a PGlite directory, so stop the dev server before running `db:migrate` or `db:seed`.
- Never edit an applied migration. Change `schema.ts` and run `npm run db:generate`. The running dev server (tsx watch) can apply a freshly generated migration right away, so never plan to edit a generated migration afterwards: when data has to be moved, first add it as its own migration (`npx drizzle-kit generate --custom`) and stop the dev server while generating.
- Numeric columns use `mode: 'number'`, so prices and money come back as JS numbers.

## Domain rules

- **Markets:** the app supports CFD, futures (E-mini and Micro) and, since 2026-10-16, crypto on all three venues (owner: "for everyone"): crypto CFDs `BTCUSD`/`ETHUSD` (1 lot = 1 coin, point = 1 USD per lot), CME `BTC1` (5 BTC, 5 USD tick = 25 USD), `MBT1` (0.1 BTC, 0.50 USD), `ETH1` (50 ETH, 0.50 tick = 25 USD), `MET1` (0.1 ETH, 0.05 USD), and exchange perpetuals `BTCUSDT`/`ETHUSDT` on the third market `crypto` (Binance, Bybit, OKX…: sized in coins from 0.001, `sizeStep('crypto')`, presets 0.001/0.01/0.1/1, the size unit is the coin via `coinOf()`, settled in USDT and counted as USD; leverage and the margin preview apply like CFDs; no daily spread question). A prop account can be on the `crypto` market too. Broker and exchange symbols are matched in `brokerSymbolCandidates()` (`BTCUSDm`, `Bitcoin`, `BTCUSDT.P`, `BTC-USDT-SWAP`, `ETH/USDT:USDT`, Tradovate `MBTZ6` → `MBT1`; a bare `BTC`/`ETH` in a signal means the CFD). The calculator has Bitcoin (BTCUSD ↔ BTC1/MBT1, alert 100 pt) and Ethereum (ETHUSD ↔ ETH1/MET1, alert 8 pt) pairs, measured from Capital.com's CFD or Yahoo's spot (`BTC-USD`) against `BTC=F`/`ETH=F`; analysis uses Capital.com's `BTCUSD`/`ETHUSD` candles (perpetuals use the coin's CFD candles, CME the CFD's shifted by the basis). Logos `public/logos/btc.svg` and `eth.svg` are drawn for the app. Fees and funding of exchanges are not counted yet (part of the planned commissions); exchange CSV imports are still to come. An instrument has `market` (cfd: sized in lots, futures: in contracts), `measureUnit` (pip for forex and gold, including gold futures GC1/MGC1 whose 0.10 tick is the gold pip, point for CFD indices, tick for the other futures), `unitSize` (the price move of one unit) and `unitValue` (quote-currency value per unit per lot or contract). The defaults are in `src/db/seed-data.ts`, for example XAUUSD pip 0.1 = $10/lot, US100/US30/US500 point = $1/lot (this varies by broker), NQ1 tick 0.25 = $5 and MNQ1 = $0.50, and the forex majors (EURUSD, GBPUSD, USDJPY, USDCHF, AUDUSD, USDCAD, NZDUSD: `assetClass` forex, pip 0.0001 or 0.01 for JPY pairs, 10 units of the quote currency per pip per lot, both currencies in `instrument_currencies`). The calendar shows more than two forex pairs as one "Forex · n" chip. Signal symbols are normalized through aliases (`normalizeSymbol`: NAS100 → US100, NQ1! → NQ1…).
- **Long is blue (since 2026-10-24, owner's rule):** BUY/long is drawn blue everywhere a direction shows (`--long`, `--long-soft`: the BUY buttons, LONG badges, recent trades, import preview, calculator, backtesting, sentiment "buyers", chart entry lines); green (`--buy`) stays for gains, wins and take profits, red for SELL/short, losses and stops.
- **Parts of a position** (partial closes, since 2026-10-05): the total size is set on the trade; closed in parts, each part (`trade_exits`, named for history) has its own size, take profit, stop loss (defaults to the previous part's) and result: `tp` (closed at its TP), `sl` (at its SL), `be` (at the entry, or at a price given since 2026-10-24: breakeven is rarely exactly zero; the form's BE shows a close-price box whose empty value means the entry), `manual` (any price) or `open`. The API takes `parts` (price only for `manual`) or, from older clients and the MT5 import, a single `exitPrice` = one part closing everything. Parts may not exceed the position (`partsTooLarge`). The trade's `stopLoss` is the first part's (the initial risk) and `takeProfits` lists the parts' TPs (`takeProfit` = the first). **Pips add up across the closed parts** (+100 and +200 = +300), money follows each part's size, R is that money against the whole position's risk, and the planned RR is the parts' planned profit against that risk. While a part is open the trade is open with `partial: true` and the realised result; once all are closed `exitPrice` is their size-weighted average and `closedAt` the last close, and only then does it count in stats. A trade in parts is **one trade** everywhere (list, stats, streaks, win rate); the per-part pips appear only in the trade's own summary. Trades saved before parts have no rows: the view shows them as one part. Each trade also has `session` (`tradeSession()` from the opening time: asia, london, overlap, newyork, off), and optionally `strategyId` with `checkedRuleIds` (`ruleCheck` in the view).
- **Trades page** (web `/transakcje`, `features/trades/`): the add form on top (`TradeComposer`), in the order a trader thinks: direction, instrument, account, open time with the session shown; the **size** (`PositionSize`: the owner's algorithm, presets 0.01 / 0.1 / 0.5 / 1 (futures 1 / 2 / 3 / 5), ×2, and "+step" where the step follows the size chosen before the "+" clicks: under 0.1 lot → 0.01, under 1 → 0.1, from 1 → 1; under it "from risk", % of the balance or an amount → a size via `sizeForRisk()` with a "Use" button, the size field staying the one source of truth; the last size is remembered per instrument); entry, stop loss and take profit; the result (open / TP / SL / BE / other price + close time) for the whole position, or "close in parts" (`PartsEditor`, a table with one grid for header and rows: size, TP, SL where empty copies the part before, result, close time; "split equally", "+ add part" with what is left). **A position can be split only when each part can be at least one step** (`canSplit()`, `sizeStep()`: 0.02 lot or 2 contracts; a 0.01 lot position cannot be split), and part sizes must be whole steps (`isWholeSteps()`); the API enforces both (`partsTooSmall`, `partSizeStep`). A summary strip (risk, planned RR, result with per-part pips, margin) is always in view with dashes until known. **The chart beside the form (since 2026-10-24, Pro and VIP; not in the demo; mockup board 7 of https://claude.ai/artifact/CAXyzLEWQxsWzpg5AtLPJR):** once an instrument with candles is chosen, `features/trades/TradeChart.tsx` shows them (the analysis's `GET /analysis/market/:id`, M1/M5/M15/H1/H4, remembered per browser) beside the fields from `2xl` (sticky), above them below that. The entry (blue for BUY, red for SELL, solid), the stop (red, dashed) and each take profit (green, dashed) are lines labelled with money and R; they are dragged with the mouse or a finger (`TradingChart` `editLines` + `onLineDrag`: a pointer within a few pixels of a line grabs it, the chart's panning holds still meanwhile) and each move writes the price, rounded to the tick for futures, into the form, which in turn moves the line. "+ Entry" puts it at the last price, "+ SL" about 0.8 ATR away, "+ TP" at 1.5R, 2.5R… from the entry, "− TP" removes the last one; a second TP turns the position into parts split equally (`tpNeedsSize` when the size cannot hold a step per part), and the parts table lays itself out by its container (`@container`, a row per part from 56 rem, compact cards with size/TP/SL in a row below that), not the window. Emotions, notes, strategy rules and screenshots (`ScreenshotDrop`: drop, paste with Ctrl+V anywhere in the form, or choose; thumbnails before saving) are always in view; signal paste, source, spread and FX rate under "Advanced". The form's header has the "+ New" button (since 2026-10-13, in place of collapse/expand): it opens the form if it was folded and starts an empty one. Beside it, the same yellow tile "Import" with a down arrow (since 2026-10-21, moved there from the trade list's toolbar at the owner's request) opens the MT5/Tradovate import. The list below opens a row's editor in place. The journal page (`/dziennik`) was removed on 2026-10-24 (a trimmed copy of the statistics); its address opens Trades. Dates and times are picked with the themed `components/ui/DateTimePicker.tsx`, never the browser's own picker (its hour and minute boxes keep what is typed until left, select their value on focus and step with the arrow keys; until 2026-10-20 they padded every keystroke, so a two-digit hour could not be typed; since 2026-10-24 the panel follows its field when the page moves instead of closing, which on phones closed it as soon as the keyboard opened for the hour, and its time row wraps so "Done" stays inside the panel).
- **Derived trade columns** (`resultUnits`, `pnlQuote`, `pnlAccount`, `riskUnits`, `rMultiple`, `plannedRR`, `tradeDate`) are always recomputed by `computeTradeMetrics()` on create and update. Never write them directly.
- **Account currency** is set per user. `fxRate` (quote → account) is 1 for the same currency. For EUR/USD/GBP/PLN and the majors' quote currencies JPY/CHF/CAD/AUD/NZD (`AUTO_FX_CURRENCIES`) it is fetched automatically: the ECB rate from the day the trade closed, via Frankfurter (`services/fx.ts`), with past days cached in `fx_rates`. The trade form fetches the same rate (`GET /fx-rate`, `useFxRate`) for its risk and margin preview and shows it as the placeholder of the empty rate field. Other currencies need a manual rate, and until one is entered `pnlAccount` stays null and the API returns a warning. `fxRateSource` is `manual` or `auto`. A manual rate survives edits, and sending `fxRate: null` switches back to automatic. Tests inject a fake `FxProvider` through `buildApp({ fx })`, so they never call the network.
- **Daily spreads (CFD):** `daily_spreads` stores the spread per user × instrument × day. Before the first trade of a day, the client calls `GET /spreads/:instrumentId/:date`. If `askUser` is true, it asks for the spread, pre-filled with `suggestion` (the latest earlier day), and saves it with `PUT`. A trade copies that day's spread into `spreadUnits` and computes `spreadCost`. This is informational only: fill prices already include the spread, so P&L isn't reduced.
- **Daily numbering** ("2/26.09.2025 – SHORT") counts all of the user's trades on that local day in the user's time zone, across instruments, ordered by `openedAt`. It is computed with a window function (`selectNumbered`), never stored, and it doesn't change when the list is filtered. `maxTradesPerDay` flags overtrading (`overDailyLimit`, the "LIMIT" badge), counted per trading account like the trading monitor (`accountDayIndex`; trades without an account are their own group), while the daily number stays shared across accounts. **Per-account limits (since 2026-10-08):** an account may set its own `maxTradesPerDay` and `lossStreakAlert` (`trading_accounts`, null = the user's default from Settings → Discipline, edited in the account form); `accountLimits(user, account)` (`services/accounts.ts`) picks the limits in force, and every check uses it: `overDailyLimit`, the monitor (each group returns `maxTradesPerDay`, `lossLimit` and `ownLimits`; the top-level values are the defaults) and the dashboard's discipline checks. The losses mode (`lossAlertMode`) stays per user.
- **Emotions** are a fixed seeded list (`DEFAULT_EMOTIONS`), and a trade can have several.
- **Signals** have 1..n take-profit levels (TP1, TP2…). Signals with prices on the wrong side are rejected, while trades only get warnings. A trade linked to a signal gets `source = educator` and inherits the signal's educator.
- **Roles and plans (since 2026-10-20, owner's rules; `shared/plans.ts`):** `admin`, `pro`, `vip`, `standard` (`ASSIGNABLE_ROLES`; invites give `standard`, `pro` or `vip`, `INVITE_ROLES`). **Pro and VIP have everything** (VIP is the same as Pro for now), and so does an admin. **Standard** has the dashboard, trades and the journal with at most `STANDARD_TRADE_LIMIT` (5) trades in all (a linked trade counts once; `assertTradeRoom()`: 403 `tradeLimit`, an MT5/Tradovate import that would not fit saves nothing, `tradeLimitImport`), statistics, strategies, the plain calculator and the calendar, on **one** trading account (`accountLimit`); the analysis, backtesting (and backtesting accounts), news and the calculator PRO answer 403 `planPro` (`PLAN_ROUTES` in `plugins/current-user.ts`). Migration 0033 rebuilt the enum: `user` became `pro` (every user then kept all features, owner's choice), the educator role was withdrawn for now (its users and invites became Pro; the value stays in the database enum, so the dormant educator/signal code still compiles: only admins publish signals), `standard` was added; sign-ups get `standard` (Better Auth's default) or their invite's role, while the column's database default stayed `pro`. `/me` returns `plan: { features, tradeLimit }` and, from GET /me only, `tradesUsed`. The web app (`features/plans/PlanLocked.tsx`: `useFeature`, `PlanGate`, `PlanLocked` with "Ask about Pro" mailing support, since there are no payments yet and an admin gives the role) locks those screens and the menu's Analysis and News, opens no news stream without the news feature, says in the trade form "Standard plan: n of 5 trades" and, when full, says so at the top and disables saving, and offers no second account (nor a backtesting one) in Settings → Accounts.

- **CFD ↔ futures calculator** (web `/kalkulator`, logic in `packages/shared/src/instruments.ts`): every pair in `CFD_FUTURES_PAIRS` (US100↔NQ1/MNQ1, US500↔ES1/MES1, US30↔YM1/MYM1, XAUUSD↔GC1/MGC1), picked at the top (remembered, basis settings stored per pair), with a single-price converter and IN/SL/TP1/TP2 levels. Mini and micro are **one futures side** ("NQ1 / MNQ1": same price, same tick); the level tiles show the money per contract for both. Distances read in the CFD's unit (pips for gold, points for indices). The difference between the markets comes from server measurements ("Auto"), from two current prices, converted by point difference (`offset`) or price ratio (`ratio`), or from a point offset the user types. Futures prices are rounded to the tick, and risk and reward per contract come from the instruments' `unitSize`/`unitValue`. `services/basis.ts` fetches the futures first and then the CFD price from Capital.com when configured, **read at the futures quote's own minute** (`fetchQuoteAt`: the one-minute candle's mid price; Yahoo's futures are about 10 minutes late, so a live CFD price would skew the difference by however far price moved meanwhile; `snapshotTimeUTC` is a real UTC time unlike the market snapshot's `updateTime`), otherwise the cash index (Yahoo ^NDX/^GSPC/^DJI) or spot gold (gold-api.com), recorded in `basis_snapshots.cfd_source`; and the futures (Yahoo NQ=F/ES=F/YM=F/GC=F, the front contract on CME/COMEX, e.g. Gold Dec) every `BASIS_INTERVAL_HOURS` (default 0.25 = 15 minutes since 2026-10-15, 0 = off) and on `POST /basis/refresh`, into `basis_snapshots`. A snapshot is `live` only when both quotes are fresh and within 20 minutes of each other. Alerts compare the last two live snapshots against `alertPoints` per pair (gold 2, US100 10, US500 3, US30 30). These sources are unofficial: fine for personal use, but they must be replaced by a licensed feed before other users rely on them. Tests inject a fake `QuoteProvider` through `buildApp({ quotes })`. The screen (redesigned 2026-10-08) is three full-width rows: the measured difference as a big figure with the alert and a sparkline of recent measurements, beside the quotes, the source (Auto / two prices / manual) and the method; a price converter with two equal sides and a swap button (swapping carries the converted price over); and the levels as four tiles (entry, SL tinted red, TPs green), each with the typed price, the other market's price, the distance, the money per contract and R:R, plus the copy button.
- **Calculator PRO (since 2026-10-20, under the levels on `/kalkulator`, `features/calculator/ProPanel.tsx`):** the difference method sometimes lands on another level, because the two markets' candles differ by a point or two from candle to candle. PRO looks each typed level up on the candle it came from (`findCandleHits()`, `shared/calculator-pro.ts`: a high, low, open or close within the pair's `matchPoints` (US100 2, US500 0.5, US30 5, gold 0.5, BTC 30, ETH 2); candles exactly at the level (within a tenth of that) first, then newest first, the owner's choice "newest + list") and reads the same point of the other market's candle opened at the same time (`readAtHit()`). Without such a candle, or while the futures candle has not arrived yet, the tile falls back to the difference method from the calculator above and says so; the other matching candles are buttons to pick instead. Two charts (`TradingChart` with `sync`, a `ChartSync` from `components/charts/chart-sync.ts`: the chart under the pointer drives the other's scrolling, zoom and crosshair; `focus` centres both on the entry's candle) show the IN/SL/TP lines and the levels' candles outlined (`ChartBox.bar`), at M1/M5/M15/H1/H4 (remembered per browser). `GET /basis/pro?pair&resolution` (`services/calculator-pro.ts`) returns 1000 CFD candles from Capital.com (the analysis's stored ones) and the futures candles from **Yahoo** (`QuoteProvider.fetchCandles`, the front contract `NQ=F` etc., about 10 minutes late, H4 built from hours in UTC buckets like Capital.com's, cached a minute). The owner chose Yahoo over the Tradovate API (paid) and over the analysis's shifted CFD candles (which would only repeat the difference method); most signal levels come from older, closed candles, which the delay does not change, so it rarely matters. A matched tile shows only the candle's price (the difference method's value for comparison was dropped at the owner's request, 2026-10-20). Yahoo is unofficial: personal use only until a licensed feed. Tests fake both through `buildApp({ quotes, market })`.
- **Position size:** CFD lots can be fractional in steps of 0.01 (see the Trades page for the presets, ×2 and +step). Futures must be whole contracts, which the API enforces. The journal form has no fees field, but the API still accepts `fees`.
- **Trading monitor** (`GET /trades/monitor`, `tradingMonitor()`): per trading account (`groups`, plus a group for trades without an account when there are some today, or no accounts at all), today's trades against `maxTradesPerDay` and today's losses counted as described under "Losses warning"; the limits from the settings apply to each account separately. Each account shows a status pill (`statusOf()` in `MonitorPanel.tsx`: stop when over a limit or at the losses warning, near at the trade limit or one loss before the warning, on track otherwise); the panel's footer states the limits with a link to Settings → Discipline. One selected account gets the full monitor ("day tape", chosen 2026-10-08 from https://claude.ai/artifact/J8xThhpUsGPTQEhCFB9A3A): a verdict ("You can trade" / "Careful" / "End the session") with the reason and today's result, one slot per allowed trade filled in order with each trade's outcome and R (dashed when free, hatched red over the limit), and the counted losses as dots against the warning; "all accounts" a compact row per account with a status dot, today's result and a mini tape. Per group the API also returns `pnlToday` and `trades` (today's trades: time, symbol, outcome, R, money). When any group reaches the threshold the web app shows a page-wide banner naming the accounts. Dismissing it is stored per set of `alertKey`s, so the banner returns after the next loss.
- **Economic calendar** (`services/calendar.ts`, web `/kalendarz`): the free Forex Factory feed (`ff_calendar_thisweek.json`) only covers the current week and has no actual values. It is fetched every `CALENDAR_INTERVAL_HOURS` (default 2, 0 = off) and on `POST /calendar/refresh` (at most once every 10 minutes, because FF blocks aggressive polling). Each import replaces that FF week (Sunday to Sunday, New York time) in `economic_events`, so rescheduled events don't duplicate, and older weeks are kept, so history builds up over time. `category` comes from `categorizeEvent(title)` (shared/calendar.ts). Affected instruments come from `instrument_currencies`. The screen (`features/calendar/`, redesigned 2026-10-08 in the dashboard style, chosen from https://claude.ai/artifact/JCDYVyv76smCUzzeERJAQa) has four tiles about today and this week (`CalendarTiles`: countdown to the next high-impact event, today's events by impact, today's releases against the forecast, high/medium events per weekday), one filter bar (currency chips with flags, impact chips, type and instrument drop-downs), and three views (`CalendarViews`): **day** as a timeline (past events dimmed, a "now" line, high impact tinted red, actual/forecast/previous cells only for data releases), **week** as day cards like the dashboard's results calendar (low impact behind "+n", weekends only with events), **month** as day tiles with the high-impact titles. Impact is a soft-tinted pill (red high, amber medium, grey low) everywhere, News included; FF's flag icons are gone. Clicking an event opens `EventDetails`, a side panel with the figures, the surprise, a chart of earlier releases (`GET /calendar/:id/history`: same title and currency; a release without an actual takes the next release's `previous`) and the instruments it moves.
- **News** (`services/news.ts`, `routes/news.ts`, web `/news`, parser in `shared/news.ts`): headlines from FinancialJuice, which has no official API; both sources below are fine for personal use but must be replaced by a licensed feed before other users rely on them. The main source is the site's own undocumented guest API (`live.financialjuice.com/FJService.asmx/Startup`, with the guest token `var info = '…'` scraped from `www.financialjuice.com/home` and cached 6 h): the latest 20 headlines with FJ's tags (`Labels`, currency codes are merged into `currencies`) and the **red marking** (`important`: `Level` contains `active`, or `Breaking`), which the web app paints like FJ (`--breaking` #b80101). Its `DatePublished` has the right UTC time but sometimes a wrong day, so the day is rebuilt (`parseFjApiNews`). After a start it pages back one `GetPreviousNews` page per poll (up to 12 h) so older headlines get their marking; a headline marked red later is pushed to the stream only if under 15 min old. If the site API fails, the RSS (`feed.ashx?xy=rss`: titles only, last 100 ≈ 8 h, no marking) is used instead (`feed.mode = 'rss'`), and the first poll after a start always uses the RSS to fill the gap. Polling runs every `NEWS_INTERVAL_SECONDS` (default 60, 0 = off). `www` answers 429 to roughly the third request within a minute from one IP (every poller on the same public IP counts); `live` tolerated more. After an error the scheduler backs off (doubling, at least Retry-After, at most 10 min). New headlines go into `news_items` (unique per RSS guid, history builds up) with tags from `parseNewsTitle()`: category (`NEWS_CATEGORIES`), currencies, assets (asset classes, for the instrument filter), speaker, outlet, released value (`data`: actual/forecast/previous) and `noise` (FJElite, rate probabilities, correlation/volatility charts; hidden unless `noise=true`). Released values are matched to a calendar event (same currency, scheduled 20 min before to 3 min after, `eventTitleScore()` plus the same forecast) and fill its `actual`, which Forex Factory lacks. `GET /news/stream` is server-sent events (`event: news`, the new headlines as JSON); the web app opens it once in AppShell (`lib/news-live.ts`), so keyword and red-headline alerts (`users.newsKeywords`; sound, notifications and "alert on red" set per browser) work on every screen and the menu shows a dot for unseen matches. The screen (redesigned 2026-10-08): the feed status as a pill by the title, one filter bar above the feed (search, red only, category and currency chips with flags, instrument, noise), headlines grouped by day and hour with the category as a coloured pill (`--info` blue for central banks, `--violet` for geopolitics, the accent for data), released numbers as actual/forecast/previous cells like the calendar, and a right column that stays in view on wide screens (next calendar events with a countdown, keyword alerts).

## Accounts and login

- **Better Auth** (`apps/api/src/auth.ts`) handles e-mail + password accounts, cookie sessions (30 days), password reset and rate limits (production). It uses our tables: `users` is the Better Auth user (`name` ↔ `displayName`), plus `auth_sessions`, `auth_accounts` (the password hash sits in `providerId = 'credential'`) and `auth_verifications`. It is mounted at `/auth/*` in the API (`routes/auth.ts`), so the web app calls `/api/auth/*`. `PUBLIC_URL` must be the web app's address, and `AUTH_SECRET` (32+ characters) is required in production.
- **Sign-in lock (since 2026-10-24, owner's rule):** `SIGN_IN_ATTEMPTS` (5) wrong passwords in a row (`users.failed_sign_ins`, counted in Better Auth's `after` hook on `/sign-in/email`; a right password, even before its 2FA step, starts the count again) lock the account (`users.sign_in_locked_at`, migration 0037): the fifth answers `ACCOUNT_LOCKED` (Better Auth keeps the 401 status; the code is what the client reads), a reset link is e-mailed at once (a `reset-password:` verification like Better Auth's own), and every later sign-in, even with the right password, is refused before the password is checked until `onPasswordReset` clears it. The sign-in page then links to the reset page to send the link again; an admin's "Unblock" also lifts the lock (the users list shows "Locked after 5 wrong passwords"). Anyone knowing an address can lock that account by guessing (the owner accepted it); the e-mailed reset is the way back.
- **Passwords** follow `passwordProblems()` (`packages/shared/src/password.ts`, since 2026-10-07): at least 10 characters with a lowercase letter, an uppercase letter and a special character (neither letter nor digit). The API enforces it on sign-up, password reset and change (a Better Auth `before` hook, code `PASSWORD_TOO_WEAK`) and in `npm run user:login`; the forms tick the rules live (`components/ui/PasswordRules.tsx`). Passwords set before the rule keep working until changed.
- **Two-step sign-in (2FA, optional per user):** Better Auth's `twoFactor` plugin with authenticator-app codes (TOTP) and 10 backup codes, both stored encrypted with `AUTH_SECRET` (`auth_two_factors`, `users.two_factor_enabled`). Settings → Profile turns it on (password → QR code from `components/ui/QrCode.tsx` (uqr) and the key → first code → backup codes shown once, to copy or download), off, or replaces the backup codes. With it on, `/auth/sign-in/email` answers `twoFactorRedirect` without a session, and the sign-in page asks for the code (or a backup code), optionally trusting the browser for 30 days. Ten wrong codes lock the account for 15 minutes. An admin can turn it off for a user who lost both (`POST /admin/users/:id/two-factor/reset`, ends their sessions).
- **Account activation (since 2026-10-15):** a new account must open the e-mailed link before it can sign in (`requireEmailVerification`). ## Security

- **Authorization by route, never by the raw URL:** `req.url` is the raw path, and a percent-encoded one ("/%61dmin/users") reaches the same route. The public paths in `plugins/current-user.ts` are matched on `req.routeOptions.url`, and `/admin/*` is checked by a hook that runs for every route of `routes/admin.ts`. A real bypass of this kind existed until 2026-10-07; the admin panel test covers it.
- **Request limits** (`@fastify/rate-limit`, `buildApp({ rateLimits })`, off in tests unless a test turns them on): 1200 requests a minute per client IP (never per cookie, which a client could make up) (`clientIp()`: `CF-Connecting-IP` behind Cloudflare), lower on costly routes through `config.rateLimit` (basis refresh 3, calendar refresh 5, MT5 import 10, screenshot upload 30, admin password reset and news refresh 5, invites 20 a minute). A refusal is 429 `tooManyRequests`. Give any new route that calls outside services, sends e-mail or parses files its own lower limit. Better Auth keeps its own limits on sign-in, sign-up and password reset. The news stream allows `MAX_STREAMS_PER_USER` (8) open connections per user.
- **Uploaded archives:** `xlsxRows()` refuses an .xlsx whose read parts declare more than `MAX_UNPACKED_BYTES` (64 MB) unpacked, so a zip bomb cannot exhaust memory.
- **Outside data:** news links reach the client only as http(s) (`webLink()`).
- **HTTP headers** come from Caddy (`deploy/docker/Caddyfile`, same block in `deploy/Caddyfile`): visitors on plain http (Cloudflare's `Cf-Visitor`) are redirected to https, plus CSP (`script-src 'self'`, no inline scripts; `style-src` allows inline because components set style attributes), HSTS, `X-Frame-Options: DENY`, `nosniff`, Referrer-Policy, Permissions-Policy. A new outside resource (font, script, image host, API) needs the CSP extended or it will be blocked in production while working in development.

## Conventions

- Money in the web app goes through `formatAmount(value, currency)` (`lib/format.ts`): USD amounts are written with `$` ("+$1215,00") and never with the code "USD"; other currencies keep their code after the number. Separate currency captions use `currencyLabel()`, which is empty for USD. Instrument prices stay plain numbers.
- Validate every request with a Zod schema from `@trading/shared` so clients can reuse it.
- Throw `HttpError` / `notFound()` / `badRequest()` from `src/errors.ts`. Validation errors come back as `{ error, issues[] }` with status 400.
- Every query on user data must filter by `req.user.id`.
- Screenshots are saved to `UPLOAD_DIR` and served at `/files/<key>` only to the owner of their trade (404 for anyone else, `Cache-Control: private`). Uploads are recognised by their first bytes (PNG, JPEG, WebP), never by the type the browser declares. They should move to S3/R2 later.
